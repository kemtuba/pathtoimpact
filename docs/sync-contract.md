# Sync contract, version 1.0.0

This is the contract between the portal in this repository, served at pathtoimpact.us, and Kem's engine on the Mac. It is written for the engine side. It restates section 4 of docs/implementation-plan.md (draft 1.3) as a standalone document, with the limits taken from src/lib/limits.ts. The reference client is engine/sync.py, which Kem copies into the Career vault.

The version number is CONTRACT_VERSION in src/lib/limits.ts, and ping reports it.

## Status

As of 23 Oct 2026 this repository holds the M0 skeleton, and only one endpoint exists in it.

| Part | State today |
|---|---|

| Every other endpoint below | Specified, not built yet. Until each one ships it answers 404, and sync.py stops with exit code 8 |

| X-Sync-Version | A major other than 1 is refused with 400 and code `validation`. A request without the header is accepted for now |
| `env` | The value of SYNC_ENV: `production`, `staging`, or `development` when SYNC_ENV is unset, as on a local `next start` |
| JSON Schemas | In contracts/, generated by `pnpm contracts:json` from the zod contracts in src/lib/contracts. Never edit them by hand; CI fails when they are stale. Today: events.schema.json, posting-export.schema.json, profile-mirror.schema.json, overlay.schema.json and reason-codes.schema.json. The build-push and master-push schemas come with WS4 |

The portal enforces the JSON Schemas in contracts/ plus the cross-field rules listed under each endpoint, which JSON Schema cannot express. Where a field list below and a schema differ, report it so one of them is fixed.

## 1 Conventions

- **Base URL.** The production host, or the staging host for previews: https://pathtoimpact-git-staging-kems-projects-c9c438de.vercel.app. Every path below starts with /api/sync/v1.
- **Headers.** Every request carries `Authorization: Bearer <raw service token>` and `X-Sync-Version: 1`.
- **Token check.** The portal hashes the presented token with sha256 and compares it in constant time against SYNC_TOKEN_SHA256 or SYNC_TOKEN_SHA256_PREVIOUS. Anything else is 401. Each environment has its own token.
- **Encoding.** JSON bodies are UTF-8. Timestamps are ISO 8601 with an offset. Dates are YYYY-MM-DD. Ids are text.
- **Week key.** Week keys in bodies must name a real ISO week: `2025-W53` matches the pattern but fails, because 2025 has 52 weeks. The week key is the portal's. It is the ISO 8601 week that contains the run date in the operator's timezone, except that a Sunday belongs to the following week, because the Sunday run prepares the week ahead. A Tuesday catch-up push therefore lands in the current week, not the next one. Keys look like `2026-W44`. Ping returns the key and pushes echo it. The code is src/lib/week.ts.
- **Size cap.** Every body is capped at 4,194,304 bytes (4 MiB), because Vercel caps function bodies at 4.5 MB.
- **Errors.** The error envelope is the same everywhere: an `error` object with `code`, `message` and optional `issues`. The code is one of `unauthorized`, `env_mismatch`, `validation`, `not_found`, `conflict`, `too_large`, `state`. Each endpoint below names its HTTP statuses.
- **Versioning.** Contract changes bump CONTRACT_VERSION, which ping reports. Changes within a major are additive. engine/sync.py is updated in the same pull request.
- **Ownership.** The portal is the system of record for consent, decisions and outcomes. Pulls are read-only. Engine acknowledgements are explicit calls.

Two invariants are server-side refusals, not conventions:

1. No sync endpoint can create or modify an application row or an applied date.
2. No sync endpoint can create a build.

Those rows exist only from the user's clicks.

## 2 Limits

Every number here is a constant in src/lib/limits.ts. sync.py keeps copies of the ones it enforces, and engine/tests fails when they drift.

| Limit | Value | Constant |
|---|---|---|
| Contract version | 1.0.0 | CONTRACT_VERSION, CONTRACT_MAJOR |
| Any request or response body, resume or built PDF | 4,194,304 bytes | MAX_BODY_BYTES |
| Postings per request | 200 | POSTINGS_PER_REQUEST |
| Posting excerpt | 2,000 characters | EXCERPT_MAX_CHARS |
| Posting pick_reason | 500 characters | PICK_REASON_MAX_CHARS |
| Build gate_transcript | 64 KB (65,536 bytes) | GATE_TRANSCRIPT_MAX_BYTES |
| Run log_tail | 16 KB (16,384 bytes) | RUN_LOG_TAIL_MAX_BYTES |
| Events per page | 500 | EVENTS_PAGE_MAX |
| Event settle window | 10 seconds | EVENT_SETTLE_MS |

Character limits count Unicode code points, the same count as Python's `len()` on a str.

## 3 Endpoints

All seventeen are listed in the order of the plan's table. "Repeatable" means the same call can be sent again safely.

### GET /api/sync/v1/ping

- **Request:** none.
- **Response:** `ok`, `at`, `env`, `week_key`, `contract_version`, `portal_commit`, `last_pull_at`, `last_push_at`, and `counts` with `overlays_approved_unpulled`, `build_requests`, `approved_drafts`, `events_since_cursor`, `deletions_pending`, `masters_in_review`.
- **Idempotency:** none needed. It wakes the Neon compute, so it is the first call of every run.
- **Errors:** 401.
- **Today:** `ok`, `at`, `env`, `contract_version` and `week_key` only.

### POST /api/sync/v1/runs

- **Request:** `id`, a client-made uuid; `kind`, one of `pull`, `sweep`, `fit`, `week`, `push`, `build`, `vault_create`, `profiles`, `purge`; `user_id`, optional; `week_key`; `status`, one of `running`, `finished`, `failed`; `started_at`; `finished_at`, optional; `counts`, optional; `log_tail`, up to 16 KB; `host`; `engine_version`.
- **Response:** `id`, `status`.
- **Idempotency:** upsert by `id`. Status never moves backwards.
- **Errors:** 409 on a backward transition; 422 validation.

### PUT /api/sync/v1/profiles

- **Request:** `profiles`, a list of: `id`, `name`, `description`, `node`, `ruling_status`, `status` (one of `draft`, `active`, `demoted`), `version`, `lookup_version`, `example_titles`, `form` (with `kinds`, each with `id`, `label` and `bar`; `tools`; `employer_types`; `screens_default`), `pay_range` (optional), `sha256`.
- **Response:** `upserted`, `unchanged`.
- **Idempotency:** upsert by `id`. The same sha256 is a no-op. Profiles absent from the body are untouched.
- **Errors:** 422.
- **Schema:** contracts/profile-mirror.schema.json.

- **Unique ids:** profile ids must be unique within the body, and kind ids unique within a profile's form. A repeat fails the whole request with 422.

### GET /api/sync/v1/participants

- **Request:** query `full`, 0 or 1.
- **Response:** `participants`, each with `user_id`, `vault_slug`, `state`, `timezone`; `profiles` with `is_primary`; `overlay` with the approved `version`, `sha256` and `approved_at`, plus `json` when `full` is 1; `resume` with `id`, `sha256`, `mime`, `byte_length` and `filename`, or null; `masters` with `profile_id`, `version` and `status`; `consents` with the pilot version and `retention_days`.
- **Consent:** a participant without the current pilot consent version carries `consent_stale: true` and `overlay: null`. sync.py writes nothing for them.
- **Overlay hash:** `sha256` is the hex sha256 of the overlay `json` serialised canonically: object keys sorted at every level, no whitespace, UTF-8, non-ASCII characters left as they are. Python's `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` produces it, so the engine can re-hash what it received.
- **Idempotency:** read-only.
- **Errors:** none beyond 401.

### GET /api/sync/v1/participants/{user_id}/overlay

- **Request:** query `version`, optional.
- **Response:** `user_id`, `version`, `sha256`, `json`, `approved_at`.
- **Idempotency:** read-only. Only approved versions are served.
- **Errors:** 404.
- **Schema:** the `json` object follows contracts/overlay.schema.json. Fields marked `x-report-only` are stored and shown, never scored.

### GET /api/sync/v1/participants/{user_id}/resume

- **Request:** none.
- **Response:** the raw bytes, with `Content-Type` set to the stored MIME type, `Content-Disposition` with the original filename, `X-Sha256` and `Content-Length`. At most 4,194,304 bytes.
- **Idempotency:** read-only.
- **Errors:** 404.

### PUT /api/sync/v1/participants/{user_id}/vault

- **Request:** `vault_slug`, `created_at`, `template_version`.
- **Response:** `user_id`, `state`.
- **Idempotency:** repeatable.
- **Errors:** 404; 409 if the participant is not `intake_approved` or later.

### GET /api/sync/v1/events

- **Request:** query `after`, a bigint cursor; `limit`, up to 500.
- **Response:** `events`, each with `id`, `kind`, `user_id`, `at`, `payload`; `next_after`; `has_more`.
- **Idempotency:** read-only and repeatable. The engine owns the cursor.
- **Ordering:** only events older than a 10-second settle window are served, so an event that commits out of sequence order is never skipped. sync.py also re-reads the last 500 ids and dedupes by event id.
- **Errors:** none beyond 401.
- **Schema:** contracts/events.schema.json. There, event ids and cursors are strings of digits, so no client loses precision on a bigint.

### POST /api/sync/v1/postings

- **Request:** `run_id`, `week_key`, `user_id`, and `postings`, up to 200 of: `external_id`, `profile_id`, `company`, `role`, `url`, `location`, `comp_min`, `comp_max`, `fit`, `fit_why`, `facets` (an object with the six facet keys), `card_json` (allowlisted keys only), `excerpt` (up to 2,000 characters), `status`, `status_date`, `source_board`, `tier_hint`, `proposed`, `rank`, `pick_reason` (up to 500 characters), `posting_date`.
- **Response:** `inserted`, `updated`, `unchanged`, `rejected` (each with `external_id` and `reason`), `week_key`.
- **Idempotency:** upsert by `user_id` plus `external_id`, as one multi-row INSERT ON CONFLICT per request. `first_seen_week` is kept and `last_seen_week` updated. Existing decisions are untouched.
- **Engine status:** the engine's `status` is stored as engine_status and never touches the portal's application state. An engine status of `applied` is accepted and changes nothing the user sees.
- **Errors:** 409 if `week_key` is not the current or previous week; 413 over 4 MB. 422 is for the envelope only: a bad `run_id`, `week_key` or `user_id`, more than 200 items, an item that is not an object or has no `external_id`, or two items sharing an `external_id`, which the one-statement upsert cannot take.
- **Per item:** each item is checked alone, first by the scrub of section 7 and then against the item schema, which also requires `comp_min` to be no more than `comp_max`. A failing item is listed in `rejected` with the scrub reason or `validation`, and the rest of the request is stored.
- **Schema:** contracts/posting-export.schema.json, which lists the facet keys and the card_json allowlist. The six facet names there are placeholders until Kem supplies the engine's own.

### PUT /api/sync/v1/participants/{user_id}/weeks/{week_key}/proposals

This is the finalize call.

- **Request:** `run_id`, and `external_ids`, the full list proposed this week.
- **Response:** `user_id`, `week_key`, `proposed`, `cleared`.
- **Idempotency:** repeatable. It sets `proposed` on the listed postings and clears it on every other posting in that week, so a pick dropped after a failed run disappears. The week is shown to the user and announced in the digest only after this call.
- **Errors:** 404; 409 if an id is unknown or the week is not the current or previous week.

### POST /api/sync/v1/coverage

- **Request:** `run_id`, `week_key`, and `rows` of `profile_id`, `seen`, `passed`, `written`, `qualified`, `proposed`, `serp_searches`.
- **Response:** `upserted`.
- **Idempotency:** upsert by `profile_id` plus `week_key`.
- **Errors:** 422.

### POST /api/sync/v1/builds/{build_id}

- **Request:** `run_id`, and `status`, one of `drafting`, `draft_review`, `building`, `uploading`, `failed`. With `draft_review`: `draft` with `keywords`, `tailored_md` and `cover_letter_md`. With `uploading`: `expected_sha256`, `filename`, `keywords`, `tailored`, `gate_transcript` (up to 64 KB), `master_sha256` and `built_at`. With `failed`: `error`.
- **Response:** `build_id`, `status`.
- **Idempotency:** transitions are validated against the build state machine. A replay of the same payload is a 200 no-op. A new `expected_sha256` is accepted while the build has not been downloaded, and after a download only as a new build revision.
- **Errors:** 404 for an unknown build, which is never created here; 409 for an illegal transition.

### PUT /api/sync/v1/builds/{build_id}/pdf

- **Request:** the raw `application/pdf` body, never base64, with an `X-Sha256` header.
- **Response:** `build_id`, `status` (`ready`), `pdf_sha256`, `byte_length`.
- **Idempotency:** if the same sha256 is already stored, the answer is 200 with `changed` false. Only this call moves a build to `ready` and sends the build-ready mail, so a run that dies between the two build calls leaves the build in `uploading`, never `ready` without a file.
- **Errors:** 413 over 4,194,304 bytes; 409 when the recomputed sha256 differs from the header or from `expected_sha256`; 409 when the build is not in `uploading`.

### POST /api/sync/v1/masters

- **Request:** `idempotency_key`, `run_id`, `user_id`, `profile_id`, `version`, `markdown`, `source_resume_sha256`, `claims` (each with `text` and `basis_hint`), `honest_gap_prompt`.
- **Response:** `master_id`, `status` (`in_review`).
- **Idempotency:** replayed from the portal's sync_receipt table by `idempotency_key`. Unique on `user_id`, `profile_id` and `version`.
- **Errors:** 409 if that version is already approved.

### POST /api/sync/v1/record-drafts

Only if decision 16 chooses engine-side pre-fill of form 3. The plan schedules it as a contract 1.1 addition, so it is not part of 1.0.0 until then.

- **Request:** `user_id`, `resume_sha256`, `json` for form 3, `idempotency_key`.
- **Response:** `record_draft_id`.
- **Idempotency:** by `idempotency_key`.
- **Errors:** 409 if the user already confirmed form 3.

### POST /api/sync/v1/deletions/{user_id}/ack

- **Request:** `vault_removed_at`, `run_id`.
- **Response:** `user_id`, `status`, one of `deleted` or `already_done`.
- **Idempotency:** repeatable. A retried ack returns `already_done` when the portal's stub is gone and the deletion log holds the user id's hash.
- **Errors:** 404 only for an id that was never deleted.

### POST /api/sync/v1/digest/send

- **Request:** `week_key`.
- **Response:** `status`, one of `sent`, `resumed` or `already_sent`; `count`.
- **Idempotency:** the portal claims the week's digest_run row under a lease and sends only to recipients with no email_send row for this digest, so a re-run sends only what is missing. It announces roles only for users whose push run finished and whose proposals are finalized.
- **Errors:** 409 if `week_key` is not the current week.

## 4 States the contract refers to

The code is src/lib/contracts/states.ts.

- **Participant `state`:** `invited`, `password_set`, `intake_in_progress`, `intake_submitted`, `changes_requested`, `intake_approved`, `vault_created`, `master_in_review`, `master_approved`, `active`, `paused`, `deletion_requested`, `vault_pending`, `deleted`. sync.py writes nothing for a participant in `deletion_requested`, `vault_pending` or `deleted`, so it never recreates a folder Kem is removing.
- **Build `status`:** `requested`, `drafting`, `draft_review`, `approved_draft`, `building`, `uploading`, `ready`, `downloaded`, `sent`, `cancelled`, `failed`. "Stalled" is derived, never stored: a build that has been `ready` for 7 days with no application. The legal transitions are `buildTransitions` in states.ts. The engine moves a build only through POST /builds/{build_id} and the PDF call, and only the PDF call sets `ready`. `requested`, `approved_draft`, `downloaded`, `sent` and `cancelled` come from the user's actions in the portal.
- **Master `status`:** `in_review`, `approved`, `superseded`.

## 5 Event kinds on the stream

| Kind | Payload | Written by |
|---|---|---|
| overlay.approved | user_id, version, sha256 | operator approve action |
| resume.uploaded | user_id, resume_id, sha256, replaces_sha256 or null | upload route |
| decision.recorded | decision_id, posting_id, external_id, decision, reason_code, text, disputed, week_key, at | decide action |
| build.requested | build_id, posting_id, external_id, needs_draft_review, requested_at | ask-for-resume action |
| build.draft_approved | build_id, approved_draft json | draft approval action |
| build.cancelled | build_id | cancel action |
| application.confirmed | application_id, posting_id, external_id, build_id, applied_on, applied_tz, via, referral_name, tier, confirmed_sha256, master_sha256 | I applied action |
| reply.recorded | reply_id, application_id, external_id, kind, on, note | reply action |
| master.approved | master_id, user_id, profile_id, version, sha256 | master approve action |
| survey.answered | survey_id, user_id, week_key, question_id, answer | survey page |
| participant.paused, participant.resumed | user_id | operator |
| deletion.requested | user_id, vault_slug, requested_at, reason | delete action or retention cron |

Each event is written in the same database batch as the primary write, with user_id stored as text and no foreign key.

Payloads are personal data: decision text, referral names, reply notes, survey answers and approved drafts. Deletion therefore purges the user's event rows at request time and keeps only the deletion.requested event. The vault ack removes that one too.

The engine must apply events idempotently, keyed by event id, because a vault restored from a snapshot rewinds its cursor and replays them.

The reason codes a decision carries are in contracts/reason-codes.schema.json: the scope's ten, plus `verdict_wrong` for a dispute. Its `x-mapping` names what each code tunes.

## 6 The order sync.py calls them

### Sunday, from the Mac

1. **ping.** Stop if `env` or the contract major does not match what the key file expects.
2. **pull.** Fetch participants. Write overlay.json for any approved version newer than the local copy. Download a resume whose sha256 differs. Read events after the cursor into inbox jsonl files, and advance the cursor only after the files are written.
3. **vault-created** for each newly approved participant, after the Makefile builds the vault from the template.
4. **run sweep** around the one shared sweep.
5. **Per vault:** run fit, then push-postings in chunks, then finalize-proposals with the full list.
6. **push-coverage**, once for the sweep.
7. **ack-deletion** for each deletion in the inbox, after the vault folder is gone.
8. **digest-send.**
9. Kem logs time in /admin.

A skipped week needs none of this. The next ping shows the whole backlog, and one pull catches up.

### A build request, on weekdays

1. Pull picks up build.requested.
2. If `needs_draft_review` is true, Kem pushes the draft with status `draft_review` and waits for build.draft_approved on a later pull. Otherwise Kem builds.
3. push-build with status `uploading` and the expected hash, then the raw PDF.
4. The portal verifies the hash, moves the build to `ready` and emails the user.

## 7 Export scrub rules

The portal rejects a postings item when:

- any string field other than `url` has a filesystem path shape: `/Users/` or `/home/` followed by a name and a slash, or `~/`, at the start of the string or after any character that cannot end a URL host or path segment, such as whitespace, a quote, a bracket, `=`, `,`, `:` or `/`. That catches markdown links and `file://` URIs. A letter, digit, `.`, `~`, `%` or `-` before the slash means a URL path, so a careers URL with /home/ in it passes;
- `card_json` contains a key outside the allowlist in contracts/posting-export.schema.json;
- the excerpt exceeds 2,000 characters;
- the item's user_id differs from the body's user_id;
- any string contains another participant's user_id;
- the url is not http or https.

A database CHECK constraint repeats a strictly narrower version of the path rule, so the per-item rejection always fires first and one bad item never aborts the whole insert.

The engine does its own scrub pass first. contracts/posting-export.schema.json holds every item to the item schema, so the engine can check its own export before sending; the portal still rejects a failing item alone rather than the whole request.

## 8 The reference client

engine/sync.py is the reference client. Kem copies it into the vault and copies it again whenever the contract changes.

- Python 3.9 or later, which has zoneinfo. Standard library only, so there is nothing to pip install. A CI job byte-compiles it and runs engine/tests on Python 3.9, so the floor is proven rather than assumed.
- One function per endpoint.
- Automatic chunking to 200 postings.
- Client-side refusal of any file over 4,194,304 bytes, with a plain message.
- A 30 second timeout, and three retries after 2, 4 and 8 seconds on connection errors, timeouts, 5xx and 429. Never on other 4xx. The first Sunday call pays the Neon cold start.
- Distinct messages for 401, 409, 413, 422 and env_mismatch.
- The cursor file advances only after the caller's callback returns.
- Configuration from SYNC_URL and SYNC_TOKEN, or from the vault's gitignored key file, with separate entries for production and staging.

engine/README.md has the key file format, the layout pull writes, the Makefile targets and the exit codes.

## Changing this contract

- Bump CONTRACT_VERSION in src/lib/limits.ts. Within a major, changes are additive only.
- In the same pull request, update src/lib/contracts, run `pnpm contracts:json` and commit contracts/, update this document, and update engine/sync.py and its tests.
- Under decisions 8 and 25, Kem reviews and merges every pull request that changes this contract. Sessions do not merge those.
