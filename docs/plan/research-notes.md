Implications the agent drew:

- Plan eligibility (decision for the user): Hobby is defensible ONLY if the portal is genuinely free, has no payments/ads/affiliate links, is built and operated by unpaid people, and does not advertise or funnel to the owner's paid business. The fair-use test is about financial gain of 'anyone involved in any part of the production', not about the owner's other businesses, but a Vercel staff reply treats a site that promotes one's own services as commercial. So: either (a) keep the tool unbranded (no CTA/link to the business, no 'built by <business>' footer that sells services) and document that intent, or (b) budget Pro at ~$20/mo per seat from day one and remove the ambiguity. Enforcement on Hobby is a feature pause, not a bill, so an incorrect call is reversible but disruptive.
- Storage (resumes and built PDFs): use Vercel Blob, not Postgres bytea. Bytea forces every upload and download through a Vercel Function, so uploads >4.5 MB fail with 413 regardless of plan, downloads >4.5 MB require streaming, and each byte burns function invocations/memory. Blob gives browser-to-Blob client uploads and direct URL downloads that never touch the 4.5 MB cap. Free-tier storage is 1 GB either way (Blob 1 GB; Neon Free 1 GB/project), so at 1-3 MB per resume plan for ~300-700 files before you need Pro or a retention policy; keep only the latest resume per user and delete superseded blobs (deletes/uploads are 'advanced ops', 2,000/mo free). Store only metadata + blob URL/pathname in Postgres.
- Uploads: implement the client-upload flow (@vercel/blob/client upload() in the browser, a Route Handler calling handleUpload()). In onBeforeGenerateToken: require an authenticated session, set allowedContentTypes to application/pdf and application/vnd.openxmlformats-officedocument.wordprocessingml.document, set maximumSizeInBytes (e.g. 10 MB), and use addRandomSuffix / unguessable pathnames. Do not accept the file via a Server Action or Route Handler body. Any post-processing (DOCX/PDF text extraction) runs in a function that fetches the blob back from Blob (outbound fetch is not subject to the request-body cap) inside the 300 s Hobby ceiling.
- Built PDF download: do not return a generated PDF directly from a function unless you stream it; the safe pattern is generate in a function (Fluid compute, <=300 s on Hobby), put() to Blob, then redirect or hand the client the Blob URL. Blob downloads count against the 10 GB/mo Hobby data transfer (shared with other Vercel usage) and simple ops only on cache misses. If the PDFs contain PII, decide on access control (see open question on private Blob access) since Blob URLs are public-but-unguessable by default.
- Weekly digest scheduling: a single Vercel Cron entry in vercel.json (e.g. '0 14 * * 1' = Mondays 14:00 UTC) is allowed on Hobby (weekly is coarser than the once-per-day minimum) but will fire anywhere in the 14:00-14:59 UTC window and is best-effort (may skip or double-fire). Design the handler idempotently: compute the ISO week key, insert a 'digest_run' row with a unique constraint before sending, and skip if it exists; verify the Authorization: Bearer $CRON_SECRET header; keep the whole run under 300 s on Hobby by batching sends (email provider batch API) and, if the user base grows, splitting into pages processed across successive daily cron runs or a queue. If minute-precise or more-than-daily scheduling becomes a requirement, that alone forces Pro (per-minute precision) or an external scheduler (GitHub Actions cron, Upstash QStash, etc.) hitting the same endpoint.
- Email itself is not a Vercel product: pick a transactional provider (e.g. Resend/Postmark/SES) and check its free tier and batch endpoint; the cron handler should only enqueue/send, never render heavy PDFs.
- Function runtime: enable Fluid compute on the project (it is the Fluid limits, not the legacy 10 s/60 s Hobby limits, that give 300 s), and set export const maxDuration = 300 on the PDF-build and digest routes. Hobby's 4 Active-CPU-hours/mo and 360 GB-hours are modest; PDF generation with a headless browser would be the biggest risk, so prefer a pure-JS PDF library (pdf-lib / @react-pdf/renderer) over Chromium for the 'built PDF'.
- Framework: Next.js 16 is fully supported on Vercel (16.3 explicitly, 16.4.x current). Pin to >=16.4.1 for the security fixes, use proxy.ts (not middleware.ts), and expect async cookies()/headers()/params.

Implications the agent drew:

- Free plan fits the pilot numerically: 10 users x (one resume + a handful of gated PDFs) at 'a few hundred kilobytes per user' is tens of MB against 1 GB Postgres storage; 100 CU-hours/month covers ~400 hours of a 0.25 CU compute, which light weekday traffic plus a Sunday sync will not exhaust as long as scale-to-zero stays on. Watch autoscaling: Free can burst to 2 CU, which burns the allowance 8x faster; consider pinning max compute to 0.25-0.5 CU in the Neon console.
- Cold starts are unavoidable on Free (5-minute suspend, cannot be disabled): the Sunday sync from the Mac and the first user visit after any quiet period will pay a few-hundred-ms (third parties report up to 1-3 s) wake. Plan for it: set the client connection timeout to >=10 s, add retry/backoff in both the sync script (urllib) and the Next.js DB client, create the Neon project in aws-us-east-1 to match Vercel's default iad1 region, and note in the Risks section that Launch (pay-as-you-go, ~$0.106/CU-hour) lets Kem disable scale-to-zero later. An always-on 0.25 CU compute would cost ~180 CU-hours/month, over the Free allowance, so do not try to keep it warm with a cron.
- Keep 'bytea in Postgres for the pilot' (it matches Neon's own 'simpler and transactional' framing for small values and avoids the neon CLI/S3 setup), but write the per-file cap into the schema and the upload handler: ~4 MB hard cap, because Vercel's 4.5 MB function payload limit applies to both the upload request and the PDF download response that pass through route handlers; Postgres's 1 GB field limit and TOAST are not the constraint. Resumes and built PDFs are typically well under 1 MB.
- Schema details for the blob tables (resume_file.bytes, build.pdf_bytes): on stable drizzle-orm 0.45.4 declare bytea with customType (the docs' bytea() helper only exists in the 1.0 RC); store sha256, mime and byte length alongside; keep blobs in their own tables (as the plan already does) and always select explicit columns so list screens never pull TOAST chunks; optionally add a custom migration (`drizzle-kit generate --custom`) with `ALTER TABLE ... ALTER COLUMN bytes SET STORAGE EXTERNAL` since PDFs are already compressed. Never return a bytea column in a relational-query JSON select (it is cast to text).
- Egress is the Free-plan number most likely to bite: 5 GB/project/month of public network transfer includes every PDF served through the app and the Mac sync pulls. At a few hundred KB per download and 10 users this is fine, but the admin 'download everything' and the retention job should stream one file at a time, and the sync script should pull only changed rows.
- Driver decision (one of two; make it explicit in the Decisions section): (A) Neon's current Vercel recommendation: `pg` + `attachDatabasePool` from @vercel/functions + drizzle-orm/node-postgres on the pooled DATABASE_URL, module-scope pool, Node runtime route handlers (Next 16 default; edge is deprecated). Gives full interactive transactions (application + follow-up clock, consent writes, better-auth with transaction: true). (B) drizzle-orm/neon-http with `neon()` created per request: lowest first-query latency and simplest lifecycle, but no multi-statement transactions (db.transaction throws; db.batch only). If gallery-os already uses neon-http and nothing in the portal needs an interactive transaction, B is the least work; otherwise choose A. Do not mix pool-outside-handler patterns with the WebSocket Pool (it must be created and closed inside the handler, with after(() => pool.end())).
- better-auth is compatible with either driver choice: the Drizzle adapter's transaction option defaults to false and the Postgres path then never calls db.transaction. If the team picks pattern A, consider `transaction: true` so password reset and session revocation are atomic.
- Migrations: use generate + migrate (committed SQL in the repo, reviewed in PR), reserve `drizzle-kit push` for the local dev branch, and point drizzle.config.ts at DATABASE_URL_UNPOOLED. Install `pg` (at least as a devDependency) so drizzle-kit runs over TCP; add `drizzle-kit check` plus a 'migration file must be committed' diff check in CI. Apply migrations either in the Vercel build command override (`npx drizzle-kit migrate && next build`, which the Neon integration supports because DATABASE_URL_UNPOOLED is injected per deployment) or in a GitHub Action before `vercel deploy`; the build-command route is the smaller first step.
- Preview environments: use the Neon-Managed integration (Kem already has a Neon account from gallery-os; billing stays in Neon). Constraints to record: one Neon project maps to exactly one Vercel project, so pathtoimpact needs its own Neon project (Free allows 100); Free allows only 10 branches per project and extra branches cannot be bought, so enable 'Automatically delete obsolete Neon branches', add the delete-branch-action on PR close, and keep open PRs few. The optional vercel-dev branch is a good home for local development.
- Preview branches are copy-on-write forks of main, so once real users exist every preview branch contains their resumes and employment records. Decide in the plan whether previews fork production (fast, realistic, more PII copies) or use a seeded/schema-only branch; Neon documents schema-only branching but it was not reviewed here (see open questions).
- Pin versions deliberately: drizzle-orm 0.45.x / drizzle-kit 0.31.x (stable) rather than the 1.0 RC whose migration folder format differs; @neondatabase/serverless 1.2.0 if used; Next 16.4.x with Node runtime; better-auth 1.7.x with @better-auth/drizzle-adapter. Note that the Drizzle docs site now shows RC syntax, so copy examples carefully.
- Keep the Mac-side sync off the database entirely (as the architecture already states): it talks to the portal's service-token API, so driver, pooling and cold-start handling live in one place (the Next.js app). Give the sync script a generous HTTP timeout and a retry, since its first call on Sunday will wake the compute.
- Phase-4 pointer: if volumes or the 4.5 MB payload limit ever bite, the migration path is Neon Object Storage (5 GB free per project, available in aws-us-east-1, branches with the database, S3 API via neon.ts + neon deploy) with the object key stored in the same rows, or client-direct uploads; the schema can anticipate this with a nullable `storage_key` column next to `bytes`.

Implications the agent drew:

- Pin the whole auth stack to one train: better-auth 1.7.12, @better-auth/drizzle-adapter 1.7.12, @better-auth/api-key 1.7.12 (if used) and run the CLI as `npx auth@latest` (Node >= 22.12 locally for the CLI; Next 16 itself needs Node >= 20.9). Do not copy gallery-os's generated schema files: regenerate with `npx auth@latest generate --adapter drizzle --dialect postgresql` so the 1.7 account index and relation names are right, then `drizzle-kit generate` + `drizzle-kit migrate` against the unpooled Neon URL. Budget a check of which better-auth version gallery-os is on; if it is pre-1.7 the lifted auth.ts needs the 1.7 upgrade-guide pass (mostly no-ops for email/password).
- Route protection pattern for the auth workstream: (a) `proxy.ts` (not middleware.ts) with an explicit matcher for the logged-in area doing only `getSessionCookie(request)` optimistic redirects; (b) a `requireSession()` helper using `auth.api.getSession({ headers: await headers() })` called in the app layout/pages, every server action and every route handler, with `requireRole('operator')` for admin screens; (c) `nextCookies()` as the last plugin so server-action sign-in/sign-out set cookies. Do not wrap session reads in `use cache`/cacheComponents (issue #5584). Because issue #9776 (nextCookies RSC detection with proxy present) is unresolved, either leave `session.cookieCache` off for the pilot or test the proxy + RSC + server-action path explicitly in week 1.
- Email wiring: `emailAndPassword: { enabled, requireEmailVerification: true, sendResetPassword }` plus `emailVerification: { sendVerificationEmail, sendOnSignUp: true }`, each calling a small Resend sender without awaiting it (wrap with `waitUntil` from @vercel/functions per the docs' serverless note). Because the admin plugin adds user fields, add `customSyntheticUser` to keep the anti-enumeration response identical. Verification, reset and the weekly digest all count against Resend's free 100/day cap (unverified figure): 10 users is well inside it, but verify the Resend pricing page before relying on it.
- Decision 1 (invite-only, least code): recommend `disableSignUp: true` + admin-plugin `createUser` from an operator screen (create with a random password and `data: { emailVerified: true }`), then trigger the password-reset email as the 'set your password' invite. Zero extra tables and no public sign-up surface. Alternative B is an `invitation_code` table plus a ~15-line `hooks.before` guard on `/sign-up/email` if Kem prefers users to self-register with a code. Reusing gallery-os's organization-plugin invitations is the most code and does not close sign-up, so drop it unless organizations are needed for the placement side.
- Decision 2 (roles): take the admin plugin with custom access control rather than a bare role column, because list/ban/impersonate/createUser are needed anyway. Define `operator` (admin statements + impersonate), `user` (none) and `placement` (none at the auth layer; the staffing-consent table is gated in app code by role) via `createAccessControl`, set `adminRoles: ['operator']`, add Kem's user id to `adminUserIds` as a safety net, and bootstrap with `npx auth@latest create-admin`. Note: without custom ac only `admin`/`user` are valid role strings, so `placement` must be declared.
- Decision 3 (sync API auth): two viable designs. (i) `@better-auth/api-key` plugin: one user-owned key created server-side for the operator with `rateLimitEnabled: false` (or a generous window; the default is 10 requests per 24 h per key and would break sync.py), no expiry (default), `permissions: { sync: ['pull','push'] }`; `/api/sync/*` route handlers read `x-api-key` and call `auth.api.verifyApiKey({ body: { key, permissions } })` once per request (do not also call getSession; do not enable `enableSessionForAPIKeys`). Gives hashed storage, rotation from the operator UI and an `apikey` table. (ii) A single static secret in a Vercel env var compared with a constant-time check in the same route handlers: no schema, no plugin, but rotation means a redeploy and no per-key audit. The bearer plugin is ruled out (session tokens, 7-day expiry). Either way sync.py sends `Request(url, headers={'x-api-key': token})` via urllib and must handle 401 (bad/expired key) and 429 (rate limit with `tryAgainIn` ms) distinctly.
- Neon + Drizzle on Vercel: use `drizzle-orm/neon-http` with the pooled connection string at runtime and keep the adapter's `transaction` option at its default false (neon-http has no interactive transactions); accept that `revokeSessionsOnPasswordReset` and similar multi-step writes run sequentially rather than atomically. Optionally enable `advanced.database.joins: true` since the generated schema carries the relations. If Vercel cold starts matter, `rateLimit.storage: 'database'` (core limiter) and api-key `deferUpdates` with `waitUntil` are the documented serverless knobs.
- Testing/risk items to put in the first two weeks: a smoke test of proxy.ts + RSC session read + server-action sign-in on a Vercel preview (community reports of Node-proxy session checks working locally but not on Vercel are anecdotal but cheap to rule out); confirm `better-auth/cookies` resolves under Turbopack (issue #5672); confirm password-reset works for an admin-created account (create with a random password so a credential account exists).

Resend treats recurring 1-to-many content as marketing: recipients must have opted in, the digest must carry a visible unsubscribe link plus List-Unsubscribe / List-Unsubscribe-Post (one-click POST) headers, unsubscribes must be honored within 48 h, and complaint/bounce rates must stay under 0.08% / 4%.
